# 会话看板（原 Codex 监控）

在原 `codex-monitor` 插件内统一展示 Codex、DSH、Kimi 和 Claude 主会话，菜单名称为“会话看板”。无需启用单独的 Kimi 插件，不更改任何宿主、模型、机器人、Hook 或 MCP 配置。

点击侧栏“会话看板”后，在 DSH 主内容区展示看板，与 Jira Flow 使用相同的主页面切换方式；侧栏仍可正常操作，不再弹出遮罩窗口。各列独立滚动，窄面板可横向滚动查看其他列。“查看会话”保留面板内的只读预览，Esc 仅关闭预览。切换到其他页面不会停止后台完成通知。

## 多客户端会话

| 客户端 | 只读数据来源与状态判断 |
| --- | --- |
| Codex | 沿用原 SQLite 索引与 rollout 生命周期读取；默认最近 7 天、30 条，原 UUID 与审核记录保持兼容 |
| DSH | 可选接入宿主 `sessionQuery` / `sessions` 服务，读取所有模型的主会话；通过真实 `turn/start`、`turn/end` 判断状态，排除委派子会话；外部 Host / CLI 会话读取原始持久化日志，避免历史恢复补出的中断事件误判运行状态 |
| Kimi | 读取 `.kimi-code` 的索引、状态和主智能体 wire；兼容旧 `.kimi/sessions` 并排除迁移重复、归档和子会话；按实际事件判断正常完成或中断 |
| Claude | 读取 `.claude/projects` 主会话 JSONL 和 `.claude/sessions` 客户端状态；排除 subagents 与内部请求内容；最终回复 `end_turn` 作为完成事实，缺少明确结束且无活跃客户端状态时标为待确认；不添加 Hook、不启动 Claude |

环境变量 `KIMI_CODE_HOME` / `KIMI_HOME` / `CLAUDE_CONFIG_DIR` 可用于已有的自定义目录；本次实现不写入或修改这些变量。DSH 内使用 Kimi 模型的会话只归入 DSH，独立 Kimi 客户端的会话归入 Kimi。

每个来源显示最新 30 条，另保留该来源的运行记录。支持客户端筛选、子来源筛选、搜索、分页预览、复制原生会话 ID、单条和批量审核。审核只更新本插件的运行记录；提交时重新核对是否已开始新轮次，不删除或修改各客户端的原始会话。新来源使用 `dsh:`、`kimi:`、`kimi-cli:`、`claude:` 标识，避免与 Codex UUID 或其他来源冲突。

卡片顶部通过官方客户端 Logo、Agent 名称和启动来源区分 Codex / DSH / Kimi / Claude，右侧显示所属状态，任务标题单独突出展示。Logo 内置于客户端，支持离线显示；DSH 使用其他模型时仍显示 DSH 标识。图标来源见 [assets/agent-logos/README.md](assets/agent-logos/README.md)。

来源健康状态分别展示。Claude 与 DSH 的可读历史日志缺少状态事实时，卡片标为“待确认”，不因此显示“数据源部分降级”；读取失败、来源不可用或运行记录丢失仍标为“异常”。某个来源读取失败时，其他来源继续工作；保留之前已展示的条目供确认，不会当成已完成或已删除。运行期间发现的新完成轮次沿用当前 Windows / IM 通知设置，消息注明客户端；历史完成和中断不触发完成通知，不修改原通知开关或接收目标。

Claude 存活进程的当前 busy / working / running 或等待授权状态优先于会话日志；`statusUpdatedAt` 仅表示进入该状态的时间，后续工具日志不覆盖它。客户端不再忙碌后，才按明确的最终回复结束事件判断完成；进程退出后忽略残留描述文件。客户端没有提供上下文窗口上限时，显示已知输入用量和“窗口未知”，不推测上限或占比。

该扩展仅修改插件源码、测试和文档，`package.json`、`cordis.patch.yml` 与所有现有配置保持原样。重启 DSH 后加载新后端和界面。完整回归可使用支持 `node:sqlite` 的 Node 运行 `node --test *.test.mjs`，以及 `python -B -m unittest codex_monitor_test.py`；原 `package.json` 中的测试脚本未改动。

## 功能

- 默认查询本机最近 7 天、按最近活动时间倒序、最多 30 条 Codex 主会话；
- 默认查询后逐条补查未命中的持久化 `session_id`，不扫描全部历史；无法取回时在“待审核”泳道显示标题带“异常”的可审核“未知会话”；
- 展示“运行中”“待审核”“记录”三条泳道；状态事实不足的异常会话无运行记录时进入“记录”，有运行记录时进入“待审核”；
- “运行中”卡片提供“移除会话”按钮，用于清理已经停止但仍显示运行中的脏会话；只移除本轮监控标记，卡片进入“记录”，不终止实际进程或删除历史；
- 任一带有效 `session_id` 的定向刷新都会幂等建立运行记录；默认刷新发现未持久化的 `running` 会话时也会建立，包括冷启动首次发现；
- 已记录会话结束或状态无法识别时进入“待审核”，点击“审核完成”删除运行记录；状态源仍存在的卡片回到“记录”，仅运行记录占位卡直接移除；
- “待审核”列的“全部审核”按钮审核当前搜索和来源筛选范围内的记录；服务器重新读取所选会话，自动跳过重新开始运行的会话，读取失败的记录保留并提示重试；
- 支持标题/工作目录搜索、来源筛选、首次打开刷新、手动刷新和每 10 秒后台校准；已有默认刷新未结束时合并请求，不启动重复扫描；
- 客户端来源优先使用 rollout `session_meta.originator` 区分 Codex App、VS Code 和 CLI，缺失或无法识别时回退到 Codex 索引的 `source`；
- 卡片并列展示 Codex 索引记录的原始 `model_provider`、`model`、`reasoning_effort` 和缩写后的 `tokens_used`，其后展示当前可见分支的累计提问次数；统计沿 rollout `history_base` 汇总分页窗口，并按 fork 分界纳入祖先提问，活动项与历史项按 `item_id` 去重；窗口尚无历史投影时回退统计 rollout 中的真实用户提交，历史链不可完整解析时不显示；
- 所有泳道的卡片第二行都根据 rollout 最新 `token_count` 展示最近一次请求的输入 Token、模型上下文窗口及占用比例，右侧保留最近活动时间；
- 支持 `codex_monitor.py list` 查询、`refresh [session_id]` 刷新，以及 `UserPromptSubmit` / `Stop` 异步 Hook 触发默认窗口刷新；Hook 保留输入中的 `session_id` 供调试，但不把它当作私有 SQLite `threads.id`；
- `UserPromptSubmit` 延迟 500ms、`Stop` 延迟 5 秒后触发刷新，给 rollout 留出写入对应状态事实的时间；
- 已打开的看板每 5 秒读取快照，自动显示 Hook 或 CLI 触发后的刷新结果；
- 同一个 `session_id` 只显示一张卡片；
- 只读访问 `%CODEX_HOME%\state_5.sqlite`、`thread_history_1.sqlite` 和 rollout；只写插件自有 JSON，不返回完整会话正文。

“待审核”只表示最新轮次已经结束、等待人工确认，不代表业务任务已经验收。

```

M:\master\start\start-dsh.bat
```

## 会话预览（v0.4.0）

每张卡片均提供“查看会话”。右侧只读抽屉按需读取最近 30 条文字记录，向上滚动或点击“加载更早记录”继续读取；“回到最新”刷新正文。用户与助手内容支持常用 Markdown，工具与思考记录默认折叠，支持单条复制和复制会话 ID。查看不会更改审核状态。

首页接口不包含正文，关闭抽屉会取消请求并释放正文；单个抽屉最多保留 200 条记录。单条正文最多预览 24,000 字符，超大日志记录会提示跳过，图片附件仅显示占位。历史分页使用字节位置，支持 Codex 上下文窗口接续和分叉截断。

`POST /codex-monitor/conversation` 接受 `{"sessionId":"UUID","cursor":null}`，返回 `messages`、`nextCursor`、`warnings`；再次提交返回的 cursor 获取上一页。路径由本机会话索引定位，接口不接受文件路径。后台不缓存会话正文。

安装后若正在运行的 DSH 仍缓存旧插件，请重启 DSH，使前后端版本一起更新。

## Windows 完成通知（v0.5.0）

Windows 桌面版默认开启：DSH 运行期间检测到新的正常轮次结束后，以 DeepSeek Harness 名义发送系统通知，包含会话标题、来源、执行统计和最终回复摘要。关闭看板不影响监听；后台每 10 秒校准，Hook 或手动刷新也会触发检测，数据源读取较慢时会延后。系统的勿扰模式可能使通知仅进入通知中心。

DSH 来源每轮通过持久化列表一次取得全部 revision，仅重读发生变化的会话；当前 Host 的实时会话使用 `observeSession(..., { projectionMode: 'none' })`，外部会话通过只读持久化句柄读取，及时释放 observation 或关闭句柄。缓存绑定持久化服务的稳定 identity，兼容 Context 代理；旧宿主仍使用原查询接口。各来源快照包含 `durationMs`，来源数量的提示中展示最近读取耗时。

当前 Host 未加载的 DSH 会话（例如独立 CLI / headless Host 中运行的任务），使用 `sessionPersistence.open(id, 'read')` 读取原始生命周期事件，读完关闭句柄。DSH 的历史查询接口会为未结束轮次补出 `interrupted` 事件用于恢复历史，看板不能将这种补出的事件当作真实结束。原始日志有开始且没有结束时仍显示运行中；真实结束后才进入待审核，只有正常完成才触发完成通知。这里反映的是日志状态：异常退出又未落盘结束事件时，可确认任务已停止后手动移除残留运行标记，不用时间阈值伪造完成。当前 Host 内存中的会话仍优先读取实时状态。

启动前的历史结束记录、中断、未知状态和重复刷新不通知。短轮次即使没有被轮询观察到运行态，只要完成时间晚于本次监控启动也会提醒。每个会话的完成时间持久化到 `%DSH_HOME%/codex-monitor/notification-history.json`（默认 `%USERPROFILE%/.dsh`），审核操作不会清除此去重记录。通知不代表任务验收通过。

看板状态行显示通知状态并提供“测试通知”。在“通知设置”中可关闭 Windows 或 IM 通知；尚未保存通知设置时，环境变量 `CODEX_MONITOR_NOTIFICATIONS=0` 将 Windows 默认开关设为关闭。保存的设置优先于默认值。发送失败会显示错误并记录日志；同一轮次不会自动重发，以免刷屏，修复系统通知设置后可用“测试通知”验证。

实现使用 Windows 自带 PowerShell 调用 [ToastNotificationManager.CreateToastNotifier](https://learn.microsoft.com/en-us/uwp/api/windows.ui.notifications.toastnotificationmanager.createtoastnotifier)，复用已安装的 `com.deepseek.dsh` 应用标识，不安装后台服务或修改系统通知设置。每次发送限时 10 秒；插件卸载时取消尚未发送的通知并终止其自有发送进程。

升级后重启 DSH 生效。

## Windows 与 IM 双渠道通知（v0.6.0）

通过 `@xmanrui/dsh-im` 的同 Host `dshIm` 服务向已保存的目标发送文字通知，复用 IM 的登录、连接和平台路由。IM 是可选依赖，缺失或卸载时看板及 Windows 通知继续运行。插件不创建机器人、不保存机器人凭据、不启动 AI 会话。

先在“设置 → IM机器人”对应机器人齿轮中，通过“新建目标 → 从已聊过的会话选择”保存目标。打开看板“通知设置”，选择目标并开启 IM。Windows 和 IM 开关独立，保存后立即生效；“测试通知”仅向开启的渠道发送固定内容，并分别显示已提交或失败。“已提交”表示 Windows/IM 接口接受请求，不等于手机弹窗、送达或已读。正常完成通知包含下述执行统计和本轮最终回复，接收者可以看到最终回复中原本包含的路径、代码和链接；不额外附加工作目录、历史对话、思考记录或工具日志。

### IM 开始通知

现有 IM 通知开关开启且已选择接收目标时，看板发现新的运行轮次会向同一目标发送一则简短 Markdown 通知：例如“Codex 开始执行”，随后显示会话标题、来源，以及已知的模型和思考强度。开始通知只发 IM，不增加 Windows 弹窗，也不读取最终回复或额外扫描会话正文。无需新增配置，关闭 IM 即同时关闭开始与完成提醒；测试通知仍发送原有固定文案。

同一轮的重复刷新只通知一次。Kimi 的输入接收、轮次开始等连续事件共用一个开始时间，Claude 的运行、等待授权及恢复执行共用当前用户输入对应的开始时间。新轮次仍可通知，即使轮询未观察到中间的结束状态。没有明确开始事实的状态不推测为新开工。

开始通知沿用后台轮询和 Hook 刷新时机，并非零延迟。启动或重新启用 IM 前已开始的轮次不补发；如果短轮次在两次刷新间已结束，仍沿用完成通知，不在完成后补发“开始”。开始和完成共用 IM 发送队列以保持观察到的顺序，开始发送失败不会阻断后续完成通知，同一开始事件不自动重试。

开始通知按机器人和目标单独保存 `notification-history-im-start-<hash>.json`，仅记录会话 ID 与开始时间；原完成通知历史文件及格式不变。开始与完成互不占用去重记录，修改接收目标仍沿用既有目标隔离规则。

### 完成通知内容

IM 使用 DSH-IM 的 `format: 'markdown'` 统一接口；Telegram（小飞机）按其 Rich Markdown 能力展示，其他渠道由 IM 适配或回退文本，不需要新增看板配置。标题、模型等元数据会转义，最终回复保留标题、列表、代码块和链接。

- 执行时长：本轮开始至正常结束的实际经过时间，包含工具运行和等待时间，不是会话创建至今的时长。
- 执行模型、思考强度：读取本轮日志，优先展示最后记录的模型和强度；未提供的值显示“未记录”。
- Token：优先展示本轮输入与输出的近似总量，包含日志计入的缓存输入；多次模型调用会累计，不等于新增输出 Token 或计费金额。Codex 按累计计数差值，DSH / Kimi 汇总本轮用量，Claude 按消息 ID 去重。无法得到本轮用量时明确显示“会话累计，非本轮”，均缺失则显示“未记录”。
- 最终回复：只读取完成时间对应轮次的正文。超出 24,000 字符时截断并提示；未读到时显示提示，不用上一轮或下一轮的回复替代。旧版 Kimi CLI 缺少可靠完成标记时沿用原通知规则，不推测完成。

示例（数值仅为说明）：

```markdown
## Codex 轮次已完成

**修复菜单显示**

- 来源：Codex App
- 执行时长：2 分 32 秒
- 执行模型：gpt-6.1-sol
- 思考强度：max
- Token：约 12,345（本轮）

### 最终回复

已修复菜单布局，验证通过。
```

详情仅在新的完成通知通过去重后按需读取，双渠道共享结果，不加入看板列表、状态接口或通知历史文件。文件型来源最多读取末尾 8 MiB；读取超时、日志缺失或不完整时发送可用统计和缺失提示。Windows 通知保留简短正文，IM 显示上述完整格式。测试通知仍发送固定连通性文案，不读取会话。

设置保存到 `%DSH_HOME%/codex-monitor/notification-settings.json`，只包含 `windowsEnabled`、`imEnabled`、`botId`、`targetId`。Windows 继续使用原有去重记录；IM 按机器人和目标分别写 `notification-history-im-<hash>.json`。每个渠道独立处理同一完成轮次，失败不阻断另一个渠道，也不会在后续轮询中自动重发。测试通知不改变完成去重记录。启动或重新启用渠道之前的历史完成轮次不补发。

详情读取最多等待 5 秒；IM 目标查询与短消息发送最多等待 10 秒，长回复根据长度延长至最多 60 秒，由 IM 插件按渠道限制分段。超时和卸载会传递取消信号。超时可能意味着平台已接收部分或全部消息但结果未确认，不自动重发，避免连续点击测试造成重复。微信发送仍受 iLink 服务端规则与最近用户会话上下文限制；显示发送失败时先检查 IM 机器人最近消息错误，必要时从手机发送一条消息后再测试。无需开启 IM 的“会话双向同步”。

通知失败的原因直接显示在看板状态行。IM 提供带 `send-rejected` 的异常链时保留安全的平台错误码，不返回底层令牌、平台用户 ID 或原始请求。微信 `providerCode=-2` 表示 iLink 拒绝这次发送，仅凭此码不能区分会话有效期、额度或内容限制；HTTP 2xx 和长轮询在线都不代表发送成功。失败轮次仍保留去重记录，不用后台重试或心跳绕过平台限制；重启不会补发已经失败的历史通知。

## 接口列表

已核实为中断、但 rollout 缺少结束事件的陈旧运行记录，可点击“运行中”卡片的“移除会话”（v0.5.3），或调用 `POST /codex-monitor/dismiss-running`，提交该卡片的 `sessionId` 与 `observedAt`。请求期间按钮禁用，后端重新核对本轮身份，若已开始新轮次则返回 409，前端重新读取列表并提示未移除。清理只修改插件自有运行记录，将该轮移到“记录”；后续同一会话的新轮次恢复跟踪，不改变 Codex 日志或停止实际任务。按钮不会自动判断进程是否已结束，应在确认是脏会话后使用。

| 接口 | 作用 |
| --- | --- |
| `GET /codex-monitor/sessions` | 读取当前会话快照与数据源健康状态 |
| `POST /codex-monitor/refresh` | 空对象刷新默认窗口；`{"sessionId":"..."}` 定向刷新会话 |
| `POST /codex-monitor/dismiss-running` | `{"sessionId":"...","observedAt":"..."}` 清理已确认中断的本轮运行标记；状态或轮次已改变时拒绝 |
| `POST /codex-monitor/review-completed` | 审核已记录的完成/异常会话或未知持久化占位卡，删除其运行记录并重新分类或移除占位卡 |
| `POST /codex-monitor/review-all` | `{"sessionIds":["..."]}` 批量审核选中的待审核记录，返回已审核、已跳过和读取失败的会话 ID；空数组不进行变更 |
| `POST /codex-monitor/notifications/test` | `{}` 向已开启的 Windows/IM 渠道发送固定测试通知；返回 `accepted` 与分渠道 `results`，部分失败也返回 HTTP 200，调用方必须检查结果；不修改完成去重记录 |
| `GET /codex-monitor/notifications/settings` | 读取开关、所选目标、渠道状态及 IM 已保存目标列表；不返回平台路由或凭据 |
| `POST /codex-monitor/notifications/settings` | 保存完整的 `{windowsEnabled, imEnabled, botId, targetId}`；启用 IM 时核对目标是否存在，保存成功立即生效 |
